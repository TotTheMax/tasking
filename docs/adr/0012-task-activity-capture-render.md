# Task activity capture-and-render over opencode server model

For TAS-17's running-status transparency requirement, we capture-and-render opencode's stdout event stream (Option A) rather than adopt the opencode server model + `@opencode-ai/sdk` (Option B) or read opencode's internal SQLite DB (Option C).

The worker (`runDefaultSubprocess`) incrementally parses opencode's newline-delimited JSON events (`text`/`tool_use`/`step_finish`) into an in-memory `ActivityStore` ring buffer per task, exposed via `GET /api/v1/<id>/activity` and a new TUI `activity` mode (key `a`). This is near-live (events stream in as emitted; TUI polls 1 Hz, same latency as all existing TUI data), self-contained, and leaves the stable spawn-per-turn worker/scheduler/abort/timeout/retry semantics untouched with zero new dependencies.

Option B (`opencode serve` + SDK `session.messages`/`event.subscribe`/`session.prompt`) would give true-live streaming and the cleanest path to requirement 2 (real prompt-queue injection), but it is a substantial worker rewrite (spawn → server+client), reworks turn/abort/timeout/retry semantics, couples tasking to the `@opencode-ai/sdk` and opencode's server API version, and runs one opencode server port per task — too much risk to a stable daemon for a transparency feature. Option C (reading `session_message`/`part` rows from `~/.local/share/opencode/opencode.db`) couples tasking to opencode's internal SQLite schema (version-fragile) and a global shared DB, and feels like reaching into another app's internals.

Rejected alternatives are recorded so a future "true-live" or "real prompt injection" enhancement picks Option B deliberately rather than re-deriving the choice. Requirement 2 (prompt injection) is analyzed but not implemented this change; if implemented later under Option A it is turn-boundary injection (pending-message → continuation guidance), with the user's message mirrored to Jira under a `💬 {user} via TUI:` sentinel for traceability.
