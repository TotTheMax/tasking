# Feishu direct sessions deliver each turn as one updatable card, with card-action control

`feishu.direct.verbosity: detailed` originally mirrored every `tool_use` event as its own text message (one message per tool call, `🔧 ${title}` only, empty `🔧 ` when the title was an empty string), so a normal turn produced ~11 messages, showed no tool name and no input/output, and could silently drop messages during a 429 cooldown. This ADR records the replacement: **one updatable interactive card per turn** plus **buttons that act through card-action callbacks**. Work goes through OpenSpec (`openspec/changes/`); this is the decision record, not the spec.

**Per-turn card, not per-session.** Each turn gets its own card, created at turn start (it doubles as the ACK, replacing the separate "✅ 会话已创建" text), PATCHed live while the turn runs, and **sealed** when the next turn starts (the button row is replaced by a one-line stats footer; tool panels, text and collapse state are untouched). A single session-level card was rejected for two structural reasons, not aesthetic ones: (a) Feishu caps a card at 30 KB and every update resends the whole card, so a session card must trim history as turns accumulate; (b) a thread is strictly chronological, so a card posted at session start drifts to the top of the thread and gets buried under every later completion message — the newest card in a per-turn design always sits next to the newest message. Cross-turn trimming therefore does not exist; only a within-turn safety valve does (oldest panels' output shortened, then their output dropped, then whole panels summarized — fired only as the card approaches a 24 KB working budget).

**Two planes: card = process, text = result.** The card carries the turn's process (per-tool collapsible panels: status/tool/command-or-args/output tail (15 lines)/truncation marker; failures default-expanded with a red border, successes collapsed) and the session state header; the single **turn completion message** stays a plain text message (final answer + stats line + permission-rejection note) because it is the quotable, searchable result record. No `@`-mention is added: a spike measured that thread-internal new messages, new cards and card updates do **not** push a notification, but that spike used a bot-created root and a bot-initiated call — not the real shape, where the `/chat` root is user-sent and the client opens a session window for the thread (the existing Jira/direct replies are in fact observed to notify). Notification behavior is therefore left to Feishu's own semantics; if long turns turn out to be silent in practice, a `notify_mention` option is a one-line follow-up.

**Card actions ride the existing long connection, on an independent fast path.** The SDK's `WSClient` + `EventDispatcher` can register `card.action.trigger` alongside `im.message.receive_v1`, so no webhook or new ingress is introduced (matching ADR 0018's thin-adapter, SDK-free-bridge posture; the SDK's high-level `Channel` module — which bundles dedup, locking, queueing and card handling — was rejected as a second framework overlapping `CommentBridge`/`DirectSessionManager`). The callback must be answered within 3 seconds and the WS client sends the handler's **return value** as the response, so the handler does only fast in-memory state changes and returns `{ toast, card }` (the card response *is* the update — no PATCH race); slow work (deleting the opencode session, sending the result text) runs after it returns. Card actions deliberately bypass the serial message **ingest queue** (ADR 0018), whose backlog could otherwise blow the 3-second deadline. Re-delivered clicks are deduped by an in-memory `card:<message_id>:<open_id>:<action>` LRU.

**Buttons are control-only; permission approval stays out.** `⏹ 中断` (only on running cards), `🔁 重试` (latest turn only; the prompt is persisted as `direct_sessions.last_prompt`), `📄 完整输出` (latest turn only; uploads the turn's full tool detail as a file attachment, falling back to a long text message, then to a pointer at the TUI activity view), `🛑 结束` (two-step confirm rendered over the same card; `/stop` is immediate). Buttons coexist with the slash commands and are open to any group member, matching the commands' existing trust model — the destructive `/done` is guarded by the confirm step instead of by an owner check. Interactive permission approval is **not** in scope: ADR 0023 already established that it requires the `opencode serve --attach` drawer (the subprocess model structurally cannot accept a mid-run answer), so it remains a separate phase; today `ask` still auto-rejects safely and the card reports the rejection.

**Config is unchanged; the card is opt-in.** Negative `verbosity` values gain no sibling: `quiet` (final answer only), `summary` (default; one completion text per turn, no card) and `detailed` (card + completion text) keep their names and defaults, so the default deployment changes behavior not at all. The reason to keep `detailed` opt-in is the collapsible-panel client floor — Feishu clients below V7.9 render panels as a "please upgrade" placeholder, which the server cannot detect. Everything else is deliberately hardcoded (1.5 s update coalescing with immediate flush on terminal/error/`/stop`/`/done`, 24 KB card budget, 15 output lines, 1 MB per-turn full-detail cap), because an unused knob costs config surface, validation, bilingual docs and drift reporting. (2026-10-09 update: the default has since flipped to `detailed`, demoting this rationale to a documented client-version requirement — see ADR 0032.)

**Fallbacks degrade, never break.** Card creation failure, or repeated PATCH failure mid-turn, switches that turn to the **same accumulator emitting coalesced text messages** (one message per flush — never back to one-per-tool) with a WARN, without interrupting the turn; the completion message is unaffected. Card upload/permission problems are surfaced, not swallowed.

**State and recovery.** `direct_sessions` gains `card_message_id` (the latest turn's card — used to seal it at the next turn start and to finalize it on restart/expiry) and `last_prompt`, both additive `ALTER TABLE` migrations. On daemon restart, a `running` session's card is PATCHed to `⚠️ 已中断（daemon 重启）` with its already-accumulated panels kept and its buttons reduced to `🔁 重试`/`🛑 结束`; typed `/stop`/`/done` (which have no callback to return into) PATCH the card explicitly, TTL expiry marks it `ℹ️ 已过期`, and PATCH failures (recalled message, past the 14-day update window) only log a WARN.

**Consequences.** Two one-time console steps are required and can be batched into a single version publish: the `im:resource` scope (file upload) and subscribing the `card.action.trigger` callback over the long connection — both bots (production and E2E test) need them, and until they exist the features degrade as above. Testing is mock-driven for everything except the click itself: card JSON construction, coalescing, action routing, guards and dedup, adapter request shapes and the mock-driven E2E are automated, while a real button click cannot be synthesized and joins the human acceptance list (alongside `test:event-flow`). The TUI is untouched: the card is the in-Feishu view of a turn, the ActivityStore (`direct:<root_id>`) remains the local full stream — two independent data planes that must not be conflated.
