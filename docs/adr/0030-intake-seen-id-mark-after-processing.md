# intake 重投去重用持久 seen-id，处理完成后写入（与 direct-sessions 的先标记时机偏离）

事件通道处理的 intake 命令回复只受进程内存 claim 与秒级 `intake_cursor`（仅 Sweep 推进）保护，停机早于下一次 Sweep 时重启会重放旧回复。决定：`ingestMessage` 对 intake **根消息**（`root_id === null`）叠加持久 seen-id（`bridge_meta.intake_seen_ids`，有界 50，照抄 `direct_sessions.seen_ids` 存储模式），**入口查、处理完成后写**——无论处理结局（成功回复/主动放弃/已发失败回执），对齐 Sweep"游标无论结果都推进"的既有语义，保持 at-least-once：崩溃夹缝最多重放一条（= 原状），绝不静默丢输入。话题回复不写入：其桥接失败走重新入队退避重试，重试挂起时原队列项的 done 已触发、`ingestMessage` 的 await 提前返回，出口标记会把"未桥接完"的消息标记为已见，崩溃窗口丢 Jira 评论；话题消息继续由 binding 游标 / direct session 游标+seen_ids 守卫。与 direct-sessions 的**入口先标记**时机偏离是刻意的：直连会话丢消息有"中断提示 + 🔁 重试按钮"产品兜底，intake（尤其 `/issue`）没有——静默丢单的代价高于重放一条回复。被否：①全量消息先标记（上述丢失风险）；②仅"纯回复型命令"标记（需消息分类，误分一条=丢一单，UX 收益与全根消息相同）；③事件通道成功后推 `intake_cursor`（`create_time` 秒级，同秒后到消息被吞）。与 `--fresh`/冷启动探测（ADR 0016/0019，跨机去重）正交：残留旧 seen-id 无害（message_id 全局唯一不重用），`freshStartReset` 不清理。若未来 intake 长出失败可见/重试兜底，可逆转收敛为先标记时机。
