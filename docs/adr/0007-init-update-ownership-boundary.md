# init --update: tasking owns skills, user owns WORKFLOW.md

After a `tasking` upgrade, shipped skills and the WORKFLOW.md template drift from what users have, but `init` skips existing skill dirs and `--force` is a destructive full overwrite. We added `tasking init --update` as a non-destructive re-sync that respects the ownership boundary. Tasking-owned skills (canonical source `assets/skills/`) are overwritten from the package — a byte-modified user version is first backed up as `<file>.bak` plus a warning, and the user is told exactly where the backups live. All six shipped skills are synced (no workflow detection — simpler, and installing a few unused skills is harmless). The user-owned WORKFLOW.md is never written to; instead the command reports the detected workflow variant, lists new config fields (defaults rendered as YAML/JSON, e.g. `[]`, since missing fields already resolve via `DEFAULTS`) and diffs the prompt body so the human reconciles credentials/state names manually. Because a bare line diff of the prompt body gives no location context, `--update` additionally writes the full new template to the gitignored `.tasking/WORKFLOW.md.reference` (removed again on the next clean run) and prints a `git diff --no-index` hint so the human can review every change in context with their own tooling. A companion `tasking init --restore` rolls any `.bak` backup back over the current skill, giving users a friendly revert path. `--update`, `--restore`, and `--force` are mutually exclusive. The directory that holds these companions is the workflow path's directory, not necessarily cwd — see ADR 0033.
