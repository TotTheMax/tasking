# Feishu direct sessions run in fixed directories, outside the scheduler

`/chat` in Feishu starts an opencode session directly (TAS-41). Three structural decisions: (1) direct sessions bypass Jira and the Scheduler — a new `DirectSessionManager` component (sibling of `CommentBridge`, riding the same ingest queue and durable store) owns their lifecycle, because tracker-driven dispatch/retry/reconcile semantics do not fit interactive chat; (2) they run in user-owned **fixed directories** (a config project→path map, or an explicit path) — not tasking-managed workspaces, because the direct path's unique value is "operate my real repo, as it is right now", and the isolated-workspace lifecycle already belongs to the Jira path; (3) one Feishu thread maps 1:1 to one opencode session — follow-ups in the thread are continuation turns (`run -s <session_id>`), queued while a turn is running, never concurrent within one directory.

Supporting choices that follow from the same logic: no Liquid template (the user's message is the prompt), no MCP injection and no hooks (the target project's own `.opencode/` config governs permissions/LSP/formatters, while the agent/model/variant are inherited from tasking's `opencode.*` — see ADR 0023), and persistence via one thin `direct_sessions` table in the existing `bindings.db` (root_id → project/path, session_id, status, cursor). The opencode session's own display title is left to opencode's native content-based auto-titling (no tasking `--title` override), so it reads naturally in the session list/TUI. The Feishu thread + local store are the only source of truth across daemon restarts — the scheduler's "external tracker rebuilds my state" property does not exist here.

Path guardrail (human decision, grill Q2): ad-hoc path mode accepts **any existing directory** — no git-repo requirement — with an optional `feishu.direct.path_roots` prefix whitelist (default empty = unrestricted) for operators who want one; project-map directories are always allowed (operator config is the consent).

Default-on (human decision, review): direct sessions ship **enabled by default** whenever `feishu.enabled` is true — usability over opt-in gating ("程序中要有默认值，保证可用性"); the section's explicit `enabled: false` is the opt-out. An upgraded deployment silently gains `/chat` path mode; the intake-group-is-trust boundary recorded above is what makes this acceptable.

Session cleanup and TUI visibility (TAS-41 follow-up): `/done` and idle-TTL expiry now also delete the opencode session on disk (`opencode session delete`) and drop its in-memory activity/runtime, rather than leaving sessions to accumulate forever; the `direct_sessions` row is retained so later thread messages still get the one-time terminal hint. The TUI gains an independent **Direct sessions** block fed through the same `/api/v1/state` snapshot (focus cycle running → backoff → direct); selecting a session opens a direct detail and reuses the existing activity view (keyed `direct:<root_id>`), without touching the Jira running list, counts, or retry logic.

Direct-session display fields (TAS-41 follow-up): each direct session persists a human-readable **name** (the first prompt, whitespace-collapsed, 80 chars; new `direct_sessions.name` column with an additive migration) so the TUI, detail, and activity headers show something meaningful instead of a raw path. The list block shows name/status/age/per-session tokens/queue and its header shows the active **session count** (`(N)`, with `· R running` when a turn is in flight) — kept separate from the Jira `Agents` bar, whose progress bar tracks a different budget. Per-session turns/input/output/total tokens are persisted on the `direct_sessions` row and restored on startup, so a session's cumulative survives a daemon restart — consistent with the session itself (id + opencode conversation) persisting. The turn counter is bumped when a turn **starts** (so the TUI shows it while the turn runs) while tokens are added when the turn ends. The home `Tokens:` line uses a separate daemon-lifetime aggregate (never cleared on `/done`, reset on restart, like the Jira totals), since it reads as a "this run" metric. Token accounting was also de-duplicated: the manager previously summed both per-`step_finish` events and `sessionAndUsage.usage` (the same events), doubling the reported totals.

Idempotent `/chat` roots (TAS-41 follow-up): WS events are the primary ingress while `discoverIntake` is a loss backstop whose cursor only advances during a sweep, so a `/chat` root delivered by WS between sweeps can be re-listed and re-ingested after a daemon restart (the sweep runs at start / on reconnect). `/issue` already guards against this with the durable `bindings.hasRootId` check; `/chat` now does the equivalent — `handleIntakeMessage` returns a hint instead of re-creating when `direct_sessions` already has the root_id. Without it, the re-ingest called `upsertDirectSession`, which preserves the existing `session_id` (the `ON CONFLICT` update deliberately leaves it), so the original first message was re-run as a continuation (`-s <deleted session>`) and opencode exited 1 ("Session not found").

Consequences: the workspace manager, FS-safety invariants, and hooks are not engaged on this path; the trust boundary changes (the agent works in real repos; intake-group membership stands in for operator consent); per-directory turn serialization is mandatory (two concurrent `opencode run` processes in one directory would fight over the git index and file locks).
