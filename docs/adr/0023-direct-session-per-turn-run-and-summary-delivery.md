# Direct sessions: per-turn subprocess execution, summary-per-turn delivery, serve/attach as a validated drawer

Each direct-session turn is one `opencode run --dir <fixed-dir> -s <session_id> --format json` subprocess, reusing the runner's spawn/timeout/inactivity/JSON-event primitives through the existing `spawnRunner` seam; opencode's own storage holds session context, so process-per-turn loses nothing. Results are delivered as **one summary message per turn** (assistant final answer + one-line stats), not streamed — Feishu on a phone is asynchronous notification semantics; mid-run silence is correct for minute-scale turns, and errors surface immediately. A `feishu.direct.verbosity` setting (`summary` default | `detailed`) optionally mirrors each tool call, sourced from the same opencode event stream that feeds `ActivityStore`.

**Prompt invariant (human-stated, TAS-41 review)**: the direct path must behave near-natively — the user's message is the prompt **verbatim**: no Liquid template, no wrapper text, no system-prompt injection, nothing appended before or after. The per-turn "summary message" is likewise not prompt-produced — it is assembled mechanically from the `--format json` event stream (last assistant `text` event + `tool_use`/`step_finish` counts). This invariant is guarded by exact-equality command-shape tests (`buildDirectCommand` deep-equal assertions), so any future wrapping fails CI.

**Agent/model/variant inheritance (TAS-41 follow-up fix)**: the per-turn command carries tasking's operator-level `opencode.agent` / `opencode.model` / `opencode.variant` (`<command> [--auto] -s <id> --dir <dir> --agent <a> [--model <m>] [--variant <v>] "<msg>"`), exactly like the Jira worker's `buildOpencodeCommand`. Rationale: relying on opencode's own default model (which the bare command fell back to) silently diverges from `WORKFLOW.md` and can pin the direct path to an exhausted/unavailable provider, while the Jira path uses the configured model. The target project's `.opencode/` config still governs permissions/LSP/formatters; only the agent profile and model are taken from tasking config for parity. Options are only appended when non-empty, so the "user message is the sole prompt" invariant is unaffected (the message stays the final positional). No `--title` is passed: the session title is left to opencode's native content-based auto-titling so it reads naturally, rather than a fixed `feishu:<root_id>` marker that truncated to colliding prefixes.

Evidence for the fast-follow drawer (local spike, opencode 1.18.30): `run --attach` against a resident `opencode serve` emits byte-compatible event streams and cuts time-to-first-event from 2.8–6.3s (with a long tail) to a stable ~1.2s; `-s` sessions are cross-mode compatible. The spike also caught the one trap: in attach mode `--dir` is resolved on the **server**, so a run without it lands in the server's cwd — attach must always pass `--dir` explicitly. v1 ships bare per-turn run (cold start is invisible under chat notification latency); the drawer is: daemon supervises `opencode serve --port <p>` → add `--attach http://127.0.0.1:<p>` → always pass `--dir`. Serve mode is also the only route to interactive permission approval (server permission API + Feishu card callbacks): the subprocess model structurally cannot take mid-run permission answers — verified that `opencode run` **auto-rejects** `ask` permissions ("permission requested: edit (hello.txt); auto-rejecting", tool_use error event, exit 0, no hang), and that with no permission config at all it allows everything even without `--auto`.

Permission posture (human decision, grill Q1 = A + strengthened auto option): the permission stance is governed by the target project's own `.opencode/opencode.json` permission config (opencode-native; `ask` safely auto-rejects and the turn summary reports what was rejected). tasking adds a user-specifiable override: `feishu.direct.auto_approve` (default `false`), optionally overridden per project in the `projects` map — when enabled it passes `--auto`, blanket-approving everything not explicitly denied. Card-button per-action approval stays a phase-2 item batched with the attach drawer.

Session teardown and TUI block (TAS-41 follow-up): v1 originally left the opencode session on disk at `/done` and on TTL expiry, so sessions accumulated forever and never appeared in the TUI (which is built from the scheduler's `running`/`retry` state). The fix keeps the durable `direct_sessions` row (so the thread still gets its terminal hint) but deletes the opencode session and clears the `direct:<root_id>` ActivityStore buffer + in-memory runtime/totals on both `/done` and expiry. Deletion is injected from the CLI (`deleteSession`), keeping `src/direct/` free of a workspace-manager import and letting tests assert teardown without shelling out to opencode. For visibility, the TUI renders an independent Direct sessions block from an optional `directSessions` provider threaded through `buildSnapshot` → `/api/v1/state` → `RuntimeSnapshot.direct`, so both the in-process TUI and `tasking tui` (HTTP client) see it. It reuses the existing selection/focus and activity machinery (direct items keyed `direct:<root_id>`, an `a activity` view, `Esc` back) and adds only a small direct-detail renderer; it never mutates the Jira running list or counts, and focus falls back to `running` if the block empties mid-frame so dynamic re-renders cannot strand the cursor.

Activity fidelity and token accounting (TAS-41 follow-up): the direct path's `onEvent` originally mapped only `text`/`tool`/`tokens`/`title` into the ActivityStore, dropping `input`/`output`/`error`/`status`/`exit`/`durationMs`/`truncated` — so the activity detail overlay (which already renders a tool's command/output) looked empty. It now maps the full event shape exactly like the Jira worker. The same handler also stopped double-counting tokens: the per-turn `stats.totalTokens` was incremented both from each `step_finish` event and again from `sessionAndUsage.usage` (the sum of those same events), so reported totals were 2×. Tokens now come solely from `sessionAndUsage.usage` (input/output/total), accumulated per-session for the detail/list and into a daemon-lifetime aggregate for the home totals line.
