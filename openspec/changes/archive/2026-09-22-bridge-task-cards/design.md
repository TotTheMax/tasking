## Context

桥（`CommentBridge`）负责把 Jira issue 与飞书话题 1:1 绑定，并做双向评论同步与命令处理（`/issue`、`/state`、`/agent`、`/help`）。目前它对飞书一侧的输出**全部是纯文本**：`replyFlat` / `replyInThread`。

直连会话这条路径已经完成了卡片化，沉淀了可复用的模式：`buildInfoCard`/`buildTurnCard` 的卡片渲染、`replyCardInThread`/`updateCard`、两步确认（`done_confirm`/`perm_*`）、长内容投递（装得下就 PATCH，超预算转 `.md` 附件）、卡片动作去重（`claimCardAction` + 渲染序号）。

同时，平台事实已实测确认：
- 桥读话题回复/群消息时**已跳过 `sender_type === "app"`**（`comment-bridge.ts:338,368,589`），所以机器人发的卡片不会被当成用户评论回灌 Jira —— 无回声风险。
- 卡片上限 30KB（我们按 24KB 预算降级），单条消息更新 5 QPS，回调有 3 秒 deadline（WS 下 handler 返回值即回调响应）。
- Jira 评论**只追加**，不需要 PATCH 去重/序号。
- Jira browse URL 可由 endpoint 推出（`tracker.ts:388`）。

约束：不改 sentinel 去重与游标语义；不引入公网回调；卡片 markdown 是子集（无表格/标题）。

## Goals / Non-Goals

**Goals:**
- 桥的命令回执以卡片呈现（`/help`、`/issue` 列表、`/agent` 列表），且卡片不可用时回落纯文本。
- Jira 评论镜像为卡片，手机端也能读到全文（按需展开）。
- 每个 issue 一张**任务状态卡**，支持"点击 → 选状态 → 确认"的转状态流程。
- 复用直连已沉淀的卡片能力，不重复造轮子。

**Non-Goals:**
- 不改 sentinel 去重、游标、双向同步的既有语义（只改"呈现形式"）。
- 不在每条评论卡上挂转状态按钮。
- 不做评论正文的表格/标题渲染。
- 不做公网回调、不做权限白名单（本期沿用"群成员皆可 + 确认兜底"）。

## Decisions

### 1. 评论卡与状态卡职责分离，转状态只在状态卡上
评论卡只负责"呈现这条评论"（作者头 + 正文 + `📄 完整输出` + `打开 Jira`）；状态卡负责"操作这个 issue"（当前状态 + `🔀 转状态`）。
- **为什么**：评论卡是只追加的历史消息，每条都挂控制按钮会让话题被按钮淹没，且评论内容与当前状态无关。
- **替代方案**：所有评论卡都带转状态按钮 —— 噪音大、语义混乱，否决。

### 2. 转状态按钮的语义是"现在打开流程"，不是"执行预置转换"
点击 `🔀 转状态` 时**实时**调用 Jira 拉取可转换状态并渲染成按钮，点选后进入确认行（`确认`/`取消`），确认才写 Jira。
- **为什么**：这样旧状态卡上的按钮永远安全（列表是点击时拉的，不会执行过期转换），同时满足"两步确认"的可控性与手机端可用性。
- **替代方案**：把转换列表烘进卡片 —— 会过期，且 Jira workflow 变化后按钮失效，否决。

### 3. 长评论按需展开，不默认发附件
评论正文按卡片预算截断；`📄 完整输出` 按钮**仅在正文被截断时渲染**，点击后**一律上传 `.md` 并在话题内发出**（手机飞书可打开文件；验收后修订：就地 PATCH 在短评论上无感知、易被当成无反应，故统一走文件）。失败在话题内回可见错误。
- **为什么**：手机端打不开内网链接，卡片必须能自足；但默认给每条长评论发文件会让话题被文件刷屏，且"一条评论一条消息"的简洁性被破坏。
- **替代方案**：截断 + 仅链接 —— 手机用户被挡；默认发 `.md` —— 太吵。均否决。

### 4. 卡片动作按来源路由，桥侧独立去重
事件通道的 `onCardAction` 目前只转发给直连（`src/cli/event-channel.ts:32`）。改为按 `value.kind`（`direct` | `bridge`）分流：桥的动作用独立的去重表（键 = 卡片消息 id + 操作人 + 动作值 + 序号），语义与直连一致。
- **为什么**：两条路径的会话空间不同，桥动作无法交给直连处理；用同一个去重范式保证重投幂等。
- **替代方案**：桥自己做轮询式回调 —— 无公网端口约束下不可行。

### 5. 状态卡消息 id 持久化在绑定表，刷新走拉取式
在绑定记录上加一个可空列存状态卡 `message_id`（与直连 `direct_sessions.card_message_id` 同范式）。**只在飞书侧动作时**更新卡片（转状态成功后 PATCH；查看时按实时查询重建）；**不为同步 Jira 侧变更做周期性轮询**（运营决策：Jira 是唯一事实源，飞书卡片是"看的时候新"而非"永远新"）。issue 消失（404）时被动 PATCH 为已完结。PATCH 失败视为卡片失效，**重新发一张**状态卡并更新 id（自愈）。
- **为什么**：卡片是整卡替换、且删卡后 PATCH 会失败，持久化 + 自愈是唯一稳妥路径。
- **替代方案**：每次状态变化都发新卡 —— 话题被状态卡刷屏，否决。

### 6. `/state` 与状态卡合一
文本命令 `/state`（及 `/state <transition>`）保留，但"查看"路径改为发/刷新状态卡；转状态既可走文本命令也可走卡片按钮，两条入口共用同一份转换逻辑。
- **为什么**：避免"文本命令"和"状态卡"两个事实源；命令仍可用于脚本化与老习惯。

### 7. 回落策略
桥的 FeishuSource 没有发卡能力或发卡失败时，所有卡片回执回落为纯文本（与直连 `replyInfoCard` 一致），命令语义不变。
- **为什么**：mock/降级环境与真实环境行为必须一致可用，`tests/bridge-flow.test.ts` 仍能跑文本断言。

## Risks / Trade-offs

- **评论镜像变 `interactive` 是行为破坏** → 在 proposal/文档标注 **BREAKING**；`tests/bridge-flow.test.ts` 与 `comment-bridge.test.ts` 同步更新；不改 sentinel/游标，外部影响面最小化。
- **状态卡被用户删除/话题归档后 PATCH 失败** → 失败即重发新卡并更新 id（自愈），日志 WARN。
- **转状态是 Jira 写操作，3 秒回调 deadline** → 回调用 `deferAction` 异步执行，立即返回 toast；写完后 PATCH 状态卡并广播结果。
- **旧状态卡按钮并发点击/重投** → 桥侧去重 + 确认行兜底；确认时若转换已不可用，返回错误并刷新状态卡。
- **卡片预算与卡片 markdown 子集** → 截断 + `📄 完整输出`；表格类内容引导回 Jira（桌面链接按钮仍在）。
- **状态卡刷新频次影响 QPS（单消息 5 QPS）** → 仅在状态真正变化时 PATCH，不做心跳。

## Migration Plan

- 无数据迁移：绑定表新增可空列，默认 `NULL`，老绑定下次状态变化时补发状态卡。
- 回滚：revert 相关提交；绑定表多出的可空列不影响旧代码读取（SELECT * 兼容）。
- 上线后按 `/help` 与状态卡自查一次；真机验收：发评论（长/短各一）、点 `📄`、点 `🔀` 完成一次状态转换、手机端验证全文可见。

## Resolved Decisions (confirmed 2026-09-21)

- **谁能转状态**：群成员皆可 + 确认行兜底（与现有 `/state` 一致）。不引入负责人/白名单校验。
- **`打开 Jira` 的 baseUrl**：由 endpoint 推出（`tracker.ts:388`）即视为浏览器可达的用户地址，直接使用。
- **评论镜像**：卡片**替换**文本（不额外发纯文本镜像）。
- **`📄 完整输出`**：就地 PATCH 原评论卡（正文展开，作者头与按钮保留），装不下才发 `.md`。
- **状态卡字段**：issue key + 当前状态 + 负责人（不含优先级/截止日期）。
- **状态卡补发**：存量绑定延迟到下次状态变化时补发，不在启动时批量补发。
- **状态卡刷新语义（2026-09-21 追加）**：拉取式——只在飞书侧动作（转状态、查看）时刷新；Jira 侧直接改状态不主动同步，避免为同步而加轮询。
- **`/issue` 列表卡**：纯展示，不带按钮；`/agent` 列表卡带每个目录 agent + 「↩️ 默认」切换按钮（与文本命令共用逻辑）；`/help` 卡为纯参考内容**不带按钮**（验收后修订：无合适的点击语义）。
- **实现粒度**：一个 change 内按 tasks 的 1→6 顺序推进，不拆两期。
